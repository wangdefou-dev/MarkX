> 目标平台：Apple Silicon Mac（arm64）  
> 首发形态：Developer ID 签名并公证的原生 macOS `.app` + `.dmg`

> 文档状态：可进入技术验证与开发排期

> v1.2 范围更正：产品只下载带 X API 官方 `article` 字段的 **X Article**。Note Post、普通 Post 和自回复线程均不计入文章数、不导出；文档后文如仍有与此矛盾的历史设计，均以本更正为准。

> v1.4 技术方案更正：X API 只用于“按博主”发现官方 X Article 的 Post ID、标题和校验文本，不再作为最终正文与媒体来源。文章正文由用户在应用内打开 X Article 页面并显式点击保存后，按已渲染文章块顺序读取；直链和已有文章重新获取均不调用 X API。未知块、Post ID 不匹配、图片无效或发现阶段校验文本不一致时拒绝导出，不得猜测排版。后文中“只通过官方 API 获取正文”、“不使用页面读取”及直链 `/2/tweets` 的历史设计均以本更正为准。

> v1.5 交互与来源时间更正：应用默认自动导入本机 Chrome 已登录的 X 会话，仅在内存中用于非持久化采集窗口；文章排版连续稳定后自动校验、上传图片并保存，无需重复输入密码或逐篇点击保存。发布时间必须优先来自页面 `time[datetime]`，并以 Post Snowflake 源时间兜底，禁止使用发现时间或入库时间冒充发布时间。详情页提供可见的“查看文章原文”按钮，博主 ID 与博主筛选标题均可直达 X 主页。

> v1.6 阅读与侧边栏交互更正：左侧博主行不再常驻刷新、删除图标，查看主页、重新拉取和删除集中到右键菜单，降低视觉噪声；文章详情页提供 `A−`、百分比复位和 `A+` 控件，可在 80%–160% 间等比例调整正文标题、段落、列表、引用、代码、表格与图片说明，并持久记住阅读字号。

> v1.7 下载与目录切换更正：侧边栏及工具栏不再分设“添加博主”和“文章链接”入口，统一为“开始下载文章”，在同一个窗口选择单个博主、批量博主或文章链接。左下角当前保存目录可直接切换；切换时必须先检查 SQLite WAL、完整复制 Markdown、数据库、来源快照与图片缓存，逐文件校验并重写数据库中的本地绝对路径，全部成功后才启用新目录。旧目录保留；目标存在同名不同内容时拒绝覆盖并继续使用旧目录。

> v1.7.1 目录同步修正：跳过嵌套 `.DS_Store` 或 SQLite WAL/SHM 时只跳过该文件，不得跳过同目录后续的 `articles/`、图片缓存或快照。失败后重试时，仅在新旧数据库的博主与文章记录逻辑完全一致时，允许用当前源数据库替换上次失败后被 SQLite 改写页布局的目标数据库；任何业务数据差异仍必须拒绝覆盖。

> v1.8 阅读排版与列表更正：字号放大或缩小时，正文行高、段落、标题、列表、引用、代码和表格的间距与内边距必须同比联动。有序列表对旧快照缺失的 marker 自动恢复连续序号，支持嵌套层级独立计数与返回上层后续编；无序列表按层级显示不同 marker。Markdown 列表使用四空格嵌套缩进，列表结束与后续段落之间必须有空行。旧导出文件仅在校验值证明用户未手工修改时自动升级。

> v1.9 直链采集稳定性更正：页面提取器只接受 `pbs.twimg.com/media/` 下的 Article 正文媒体，必须排除头像、emoji 和 UI 图标；所有原图完成加载、媒体 ID 数量齐全且页面连续稳定后才能入库。原图下载、S3/R2 上传和公网回读必须有有界重试。失败数按文章去重而不按尝试次数累加，成功后清除；删除尚未生成 Markdown 的待采集文章时，空作者索引也必须可重建，不得留下幽灵记录。默认单博主输入框一旦识别到 Article 直链，必须自动切换到零 API 直链路径，不得误启动博主时间线扫描。

> v2.0 API 成本保护更正：Post Read 按当前官方单价 US$0.005/返回资源估算，User Read 按 US$0.010/返回资源估算。博主扫描默认上限从 300 降至 50；所有付费扫描执行前必须显示理论费用上限并二次确认，超过 US$0.50 或进入无法可靠估算的完整历史时默认拦截，只能由用户显式允许当次扫描。已存在博主默认使用 `since_id` 只查新 Post；“立即同步”每位最多查 20 条并必须先确认。任务进度必须显示已返回 Post 的费用估算。文章直链、已有文章重新获取和右侧预览仍为 0 次 X API。

> v2.1 Articles 专属列表架构更正（覆盖 v2.0 的付费发现方案）：按博主下载时，应用必须直接打开 `https://x.com/<handle>/articles`，复用本机 Chrome 登录态，自动滚动 Article 专属列表并只收集与目标博主匹配的精确 `/handle/status/PostID` 链接；禁止通过 User Posts、Search 或 Full-Archive Search 全量扫描普通 Post 来发现文章。最近范围按用户选择的 Article 数量停止，默认 10 篇；完整历史滚动至 Articles 列表底部。发现链接后沿用非持久化页面采集器逐篇保存完整排版。博主发现、正文读取和立即同步的 X API 调用均为 0；Bearer Token 仅作为旧版兼容设置保留。后文所有与此冲突的 API、Post 扫描、费用估算和“禁止 Cookie/DOM”历史设计均以本更正为准。

> v2.2 后台采集交互更正：Articles 列表和每篇正文所需的非持久化 WebKit 页面只能作为不可见运行时存在，不得向用户展示网页、登录页、浏览器工具栏或手动保存控件。发现阶段的原生进度面板必须按发现顺序实时展示文章标题与精确链接；下载阶段必须展示逐篇状态。单篇失败后继续处理队列，整个批次结束后统一报告成功、已有完整归档跳过、失败和图片数量。

> v2.4 博主导航层级更正：选中博主时，中栏最顶部导航区只保留一行“博主名称 + 查看主页”，按钮紧跟博主名称右侧；不在顶部另起一行显示 `@ID`或文章数。删除文章列表内的独立博主信息卡，列表中只展示文章条目。

> v2.5 引用文章卡片更正：正文内出现引用其他 X Article 的嵌套卡片时，必须在卡片的原始块位置只保留精确的 X `/status/` 或 `/article/` HTTPS 链接。不得把引用卡片的作者、日期、摘要、阅读量或互动数据写入主文，不得用作者主页代替被引用文章链接。无法验证精确文章链接时继续拒绝不完整导出。Markdown 和右侧预览均仅显示可点击的“引用文章”链接。

> v2.6 uPic 读取阻塞更正：应用不得直接打开 uPic 受保护的容器 plist；通过 `defaults export` 读取时必须输出到独立临时文件，不得使用可能等不到 EOF 的管道。导出超过 3 秒必须终止子进程并报告，不得让文章永久停在“正在校验页面原始排版”。

> v2.3 X DraftJS 空原子节点兼容：X 页面偶尔会残留 `<section data-block="true">` 空原子节点。只有节点同时没有子元素、没有文字、没有媒体身份并且渲染高度不超过 0.5 px 时，才可判定为不可见遗留节点并忽略；任何有子结构、有文字、有媒体链接或仍占页面高度的块都不得套用此规则，仍须等待加载或按未知块拒绝导出。

> v2.7 批量同步交互更正：右上角“立即同步”必须是独立功能，点击只打开确认窗口，不得用固定数量直接启动。用户可确认每位已跟踪博主要检查的最近 1–100 篇，默认 10 篇；该范围仅限制每位博主的文章数，不限制博主总数，必须将全部已启用的跟踪博主（包括 100 位或更多）加入队列。确认后后台读取各博主 Articles 专属列表，已通过完整性校验的文章自动跳过，仅新文章和未完成文章进入正文队列。同步过程显示博主进度、文章标题与链接、保存、跳过、失败和图片数量；结束后使用独立同步结果报告检查范围及各项数量。浏览器界面保持隐藏，X API 调用为 0。

> v2.8 同步视觉、图床快捷入口与定时同步更正：工具栏与同步弹窗必须使用同一同步图标，弹窗标题、正文、辅助文字、图标容器和卡片间距统一。左下角图床未连接状态必须可点击，直接打开并定位图床配置。同步弹窗增加“立即同步 / 定时同步”分段选择；定时模式可配置每日时间和每位博主文章数，使用用户级 macOS LaunchAgent 在应用窗口关闭时隐藏唤起。睡眠期间错过计划时间时于下次唤醒合并补执行一次；完全关机时不得宣称能执行。定时结果持久保存，已有任务运行时跳过并记录，不并发写入资料库。

## 0. 一页结论

这是一个安装在用户自己 Mac 上的原生归档工具。用户添加一个或多个 X（原 Twitter）博主后，软件批量发现其官方 X Article，将标题、完整正文、图片、链接和可获得的语义排版转换为本地 Markdown；原始图片先可靠下载到本地缓存，再上传到用户现有的默认图床，最后将远程图片 URL 写入 Markdown。

产品不是“网页批量另存为”，而是带来源约束、结构校验和原子落盘的本地归档器。它复用本机 Chrome 登录态读取 X 的 Articles 专属列表和已渲染长文页面；默认使用本机 uPic 当前选中的 S3/R2 图床，由应用内原生 Signature V4 适配器上传并取得可验证 URL。uPic 密钥默认只在运行时内存中使用；只有用户在界面明确点击“导入”时，才可将当前默认 S3/R2 配置转存到本应用 Keychain。正文不会发送给任何 AI 服务。

本需求有两个必须如实呈现的能力层级：

| 模式 | 能得到什么 | 完整性边界 | 适合场景 |
|---|---|---|---|
| 最近范围 | 从目标账号 `/articles` 专属列表读取最近 N 个 Article 链接，默认 10 篇 | 只承诺用户选择的最近 N 篇，不代表账号终身历史 | 默认、快速首次试用 |
| 完整历史 | 自动滚动目标账号 `/articles` 专属列表直至底部并收集全部可见 Article 链接 | 受当前 Chrome 登录账号可见范围和 X 页面可用性约束 | 真正要求所有可见文章的正式归档 |

“任务完成”的定义必须同时满足：正文已落盘、文章结构校验通过、应有图片数量一致、每张图已成功上传且远程可访问、Markdown 中没有临时 URL、任务检查点已提交。任何图片上传失败都不能把该文章显示为“已完成”。

## 1. 背景与问题

X 上越来越多作者使用 Articles 发布带独立标题、完整正文和多张图片的内容。现有收藏方式通常只有链接，存在以下问题：

1. 链接依赖平台在线状态，内容被编辑、删除、转私密或账号异常后难以继续阅读。
2. 逐篇复制正文效率低，标题、图片、列表、引用、代码块等结构容易丢失。
3. 浏览器“另存网页”会携带大量脚本和样式，文件难以进入 Obsidian、Git、静态博客等 Markdown 工作流。
4. 直接把远程 X 图片链接写入 Markdown，后续可能失效；手动转存图床又耗时且容易漏图。
5. 多个博主、多次归档后容易重复下载，无法判断哪些文章新增、编辑、删除或失败。
6. X 的不同 API 范围、计费和历史深度不同，如果软件只显示“全部下载”，用户无法判断归档是否真的完整。

因此需要一个可安装、可恢复、结果可验证的本地原生软件，把“发现文章 → 获取结构 → 缓存图片 → 上传图床 → 生成 Markdown → 后续增量同步”做成一条可靠流水线。

## 2. 产品目标与非目标

### 2.1 产品目标

G-01. 用户可以一次添加一个或多个公开 X 博主，批量归档其 X Article 完整内容。

G-02. 默认输出可直接阅读和二次编辑的 Markdown，保留标题、段落、标题层级、列表、引用、链接、代码、分隔线和图片顺序。

G-03. 所有文章图片使用用户默认图床的远程 URL；图床失败时保住原始图片和任务状态，支持一键续传。

G-04. 首次全量后支持增量同步，不重复生成文章，不重复上传未变化图片。

G-05. 对“最近 N 篇”和“完整历史”做明确区分，任何时候都能回答“这次从 Articles 专属列表读取了多少篇”。

G-06. 软件为真正的 macOS 原生应用，可在 Apple Silicon Mac 上安装、启动、操作和卸载。

G-07. 全流程默认本地处理，无 AI 改写、摘要或翻译，不改变作者原意。

G-08. 仅读取用户当前登录态有权查看的 X 页面，并保留作者、原文链接、发布时间等来源信息，降低平台合规和版权风险。

### 2.2 非目标

NG-01. v1 不做自动翻译、AI 摘要、改写、洗稿、标签生成或知识库问答。

NG-02. v1 不自动发布到公众号、博客、Notion、Obsidian Sync 或其他内容平台。

NG-03. v1 不下载私信、付费墙内容、受保护账号的非公开内容或用户无权访问的内容。

NG-04. 不扫描普通 Post，不调用付费时间线或搜索 API，不绕过登录、权限、付费墙、验证码或平台访问控制；仅使用用户本机 Chrome 已授权登录态读取正常可见的 `/articles` 列表和 Article 页面。

NG-05. v1 不承诺复刻 X 网页的字体、卡片尺寸、响应式布局等像素级视觉样式。

NG-06. v1 不归档 Note Post、普通短帖、转帖、回复、自回复线程和点赞列表。

NG-07. v1 不下载视频和音频正文资源；遇到视频时保留封面、说明和原帖链接，并在结果中标注“视频未归档”。

NG-08. v1 不替用户购买 X API 用量，也不在应用二进制中内置共享 X API 密钥。

NG-09. v1 不做多用户云端账号系统、跨设备云同步或团队权限管理。

## 3. 用户与核心场景

### 3.1 核心用户

主要用户是需要长期收集中文或英文 X 长文的个人创作者、研究者和知识管理用户。他们使用 M 系列 Mac，习惯用 Markdown、Finder、Obsidian 或 Git 管理资料，已经有可用图床，希望数据由自己掌控。

### 3.2 核心 Job to Be Done

> 当我发现值得长期关注的 X 博主时，我希望一次添加多个账号，可靠地把他们已有和未来新增的长文保存到自己的 Mac，并把图片转存到自己的默认图床，这样我可以在平台之外持续阅读、检索和整理，同时知道归档是否完整、哪里失败、怎样恢复。

### 3.3 典型场景

S-01. 用户粘贴 20 个 `@handle`，选择“最近范围”，软件依次打开每个账号的 `/articles` 专属列表，各读取最近 N 个官方 X Article 链接。

S-02. 用户对一位高频博主选择“完整历史”，软件自动滚动其 `/articles` 列表直至底部，随后逐篇采集完整排版，全程不调用 X API。

S-03. 文章有封面和 12 张内文图。软件先把 13 张图全部下载到缓存，再按原顺序上传 uPic；远程验证全部通过后生成最终 Markdown。

S-04. 上传第 8 张图时网络中断。已经上传的 7 张不会重复上传，其余图片保留本地；恢复网络后从第 8 张继续。

S-05. 博主编辑了标题或正文。下次同步时软件更新同一文件，保留旧版本快照，并在历史记录中说明变化时间。

S-06. 某原文从 X 删除。下次同步时软件按合规策略标记并处理，界面不再把该文件描述为当前有效内容。

S-07. 用户断网时仍可打开软件浏览已经归档的本地文章、打开 Finder、查看历史任务；只有同步与图片上传不可用。

## 4. 核心概念与范围定义

### 4.1 “文章”的产品定义

产品中的“文章”只指 **X Article**：Post 必须带有官方 `article` 字段，其中可包含独立标题、完整正文、封面、内文图片、代码或嵌入 Post。

`note_tweet` / `note_post` 仅代表超过普通字数限制的 Note Post，不是 X Article；同作者自回复线程也不是 X Article。两者不参与用户选定的“最近 N 篇”计数，不建立本地文章记录。

### 4.2 “所有文章”的定义

软件不得把“API 返回为空”或“扫描最近 3,200 条”显示为“已下载全部历史”。必须使用以下状态词：

| 完整性状态 | 判定条件 | 用户可见说明 |
|---|---|---|
| `FULL_ARCHIVE_VERIFIED` | Full-Archive Search 覆盖用户设定的起止日期，所有分页完成，无未恢复错误 | “已完成指定日期范围的完整历史扫描” |
| `RECENT_WINDOW_COMPLETE` | 用户时间线分页到 API 终点，最多扫描 3,200 条 Post | “已完成最近范围扫描；更早内容可能未覆盖” |
| `PARTIAL` | 账号、日期或分页中存在错误、限流、权限或用户主动停止 | “部分完成”，并显示缺口 |
| `UNKNOWN` | API 未给出足够信息判断范围，或技术验证尚未通过 | “无法确认完整性”，不得显示“全部” |

最近范围模式获取允许范围内的 Post，再在本地严格检查 `article` 字段；未带该字段的项目直接忽略。

### 4.3 “保留排版”的定义

“保留排版”指语义等价，而非网页截图式复制：

- 标题文字和标题层级保留；
- 段落顺序和可见文字不改写；
- 有序列表、无序列表、引用、代码块、行内粗体、斜体、删除线、下划线、链接、分隔线和表格尽可能映射；
- 封面和内文图片在相同语义位置出现；
- 嵌入 Post 使用可读引用块 + 原帖链接表示；
- Markdown 无原生等价物时允许使用最少量安全 HTML，例如 `<u>`；
- 当读取响应包含 DraftJS `content_state` 且媒体均有正文锚点时，必须逐块保留并显示“排版结构已校验”；当官方读取响应只给 `plain_text` 与媒体列表时，必须逐行、逐图无损保存并明确显示“文字图片完整 · 排版受接口限制”，不得臆造或声称已还原响应中不存在的粗体、标题层级和图片插入位置；
- 原始结构化数据保留在内部快照中，以支持未来重新导出。

不得为了“优化阅读”自动改标点、合并段落、翻译、删节或补写。

### 4.4 “默认图床”的定义

v1 中默认含义是：使用本机 uPic 当前选中的 S3 / Cloudflare R2 图床。由于 App Store 版 uPic 1.4.9 不再通过旧 CLI 的标准输出返回 URL，应用在运行时只读取 uPic 沙盒配置中的当前默认 S3/R2 参数，用内置 Signature V4 上传并回读 HTTPS URL。

默认模式不复制、不回显、不记录 uPic 密钥；每次上传只在内存中使用当前配置。只有用户明确点击“从 uPic 导入当前 S3/R2 配置”时，才可将密钥写入本应用 Keychain。手工填写原生 S3/R2 配置仍作为备选。

若没有安装 uPic，应用引导用户选择以下替代方式之一：

- 安装并配置 uPic；
- 在本应用中配置 S3 兼容存储（含 Cloudflare R2）；
- 配置 WebDAV；
- 配置可返回单个公开 URL 的自定义 HTTP 上传接口。

没有通过“测试上传”的图床不能用于正式任务。

## 5. 端到端用户流程

```text
首次启动
  ↓
选择本地归档目录
  ↓
连接 X API并测试权限/可用范围
  ↓
自动发现 uPic → 上传测试图 → 验证返回 URL
  ↓
粘贴博主账号或导入 TXT/CSV
  ↓
解析并预览账号身份
  ↓
选择最近范围 / 完整历史、日期、内容类型
  ↓
展示预计扫描量、完整性说明和可能的 API 用量
  ↓
开始任务
  ↓
发现 Post → 识别长文 → 获取结构 → 解析规范化
  ↓
下载原图到本地缓存 → 校验 → 上传图床 → 远程验证
  ↓
生成临时 Markdown → 内容与图片一致性校验
  ↓
原子写入最终 Markdown → 更新索引与检查点
  ↓
展示完成 / 部分完成 / 需操作，并可在 Finder 中打开
```

### 5.1 首次启动

首次启动只要求完成三件事：选择归档位置、连接 X、确认图床。不得先展示空白主界面后让用户到多个设置页自行猜测。

设置向导每一步都必须有：当前状态、简短说明、测试按钮、成功证据和可执行错误建议。

### 5.2 添加博主

输入支持：

- `@username`；
- `username`；
- `https://x.com/username`；
- 多行粘贴；
- 导入 UTF-8 TXT / CSV，CSV 至少支持 `username` 列。

应用解析后显示头像、显示名、`@handle`、账号公开/受保护状态和重复状态。用户确认后才入库。

主界面侧边栏必须直接提供“添加博主并下载”，不能只藏在右上角工具栏。新增窗口默认为单个博主模式，同时保留批量添加。

### 5.3 创建归档任务

任务创建页依次呈现：

1. 账号范围；
2. 内容类型；
3. 历史范围；
4. 输出目录与命名规则；
5. 图床；
6. 预计 Article 数量和完整性边界；
7. 开始按钮。

默认值应足以直接开始：单个博主、最近 10 篇 X Article、Markdown、使用当前 uPic 默认图床、保留本地图片缓存、增量同步开启。最近范围允许选择每位博主保存 1–100 篇，选定后必须显示明确的“下载最近 N 篇”按钮。

### 5.4 任务执行

任务卡片显示五段进度，而不是一个无法解释的百分比：

- 发现：已从 Articles 专属列表识别的文章数 / 当前目标博主；
- 获取：已获取文章结构 / 已发现长文；
- 图片：已下载、已上传、失败数量；
- 写入：已生成 Markdown / 待处理；
- 校验：完成、警告、失败。

用户可暂停、继续和取消。取消只停止后续工作，不删除已经完成的文章、本地图片缓存或检查点。

### 5.5 查看结果

任务结束后首先显示结果摘要：

```text
3 个博主
从 Articles 专属列表发现 126 篇
完成 122 篇
待重试 3 篇
跳过 1 篇（重复）
上传并验证 684 张图片
完整性：2 个账号为最近范围，1 个账号为完整历史
```

“全部文章”使用按发布时间倒序排列的单一平铺列表，不再为每位作者建立列表分段；作者仍作为文章行的元数据显示。用户可通过左侧博主入口只看该博主的文章，也可按“失败原因、博主、内容类型、日期、同步状态”筛选。

用户能从每篇文章执行：预览、打开 Markdown、在 Finder 中显示、访问原文、重试图片、重新导出、查看版本差异，以及通过右键菜单删除。删除必须二次确认，把 Markdown 与来源快照移入 macOS 废纸篓，并同步清理数据库记录和索引；不得自动删除远程图床文件。

### 6.1 主窗口

采用原生三栏布局：


窗口最小尺寸建议为 1,080 × 680；支持深色模式、系统动态字体、键盘导航和 VoiceOver 基本标签。

### 6.2 左侧栏

- 全部文章；
- 最近归档；
- 待同步；
- 待重试；
- 有警告；
- 已删除/不可用来源；
- 博主列表；
- 任务历史。

### 6.3 顶部工具栏

- 添加博主；
- 新建归档；
- 立即同步；
- 暂停/继续当前任务；
- 搜索；
- 设置。

### 6.4 设置页

设置按用户语言组织，不暴露不必要的技术 ID：

1. **X 连接**：已连接/未连接、权限范围、最近测试时间、最近错误、用量说明、重新连接。
2. **默认图床**：当前为“uPic：当前默认配置”、测试上传、返回域名、切换适配器。
3. **本地归档**：目录、文件名格式、是否保留原图缓存、缓存上限。
4. **同步**：并发数、重试、是否同步编辑/删除、自动同步（P1）。
5. **隐私**：零遥测说明、日志位置、清理日志、导出诊断包。

设置中不得显示完整 Token、Access Key 或 Secret。只允许显示“已配置”和末 4 位指纹；复制按钮默认不存在。

### 6.5 状态与空态

空态必须给出下一步动作，例如“还没有博主，粘贴一个 `@handle` 开始”。

错误不能只显示 HTTP 状态码。至少映射为：

- X 凭证失效：重新连接；
- 当前访问级别不支持完整历史：改用最近范围或升级 API；
- API 用量不足：查看预计读取量，稍后继续；
- 请求过快：显示可重试时间并自动排队；
- uPic 未安装：选择替代图床或安装 uPic；
- 图床上传失败：保留本地原图，一键续传；
- 归档目录权限失效：重新选择原目录；
- 原文已删除或不可见：标记来源状态并执行合规策略。

## 7. 功能需求

### 7.1 安装与首次配置

FR-001. 应用必须是原生 arm64 `.app`，在 Apple Silicon Mac 上无需 Rosetta 启动。

FR-002. 最低支持 macOS 14，针对当前 M3 Max / macOS 26.5.2 做首要实机验收。

FR-003. 首发安装包必须为 Developer ID 签名、公证并 stapled 的 `.dmg`。

FR-004. 首次启动必须通过向导选择归档目录，并保存持久访问所需的目录授权信息。

FR-005. 应用必须检测归档目录是否可写、剩余空间是否足够，并用一个可删除的临时文件验证原子写入。

FR-006. 应用必须提供 X API 连接测试，验证凭证有效、目标接口可达、可用模式和当前权限。

FR-007. X 凭证只写入 macOS Keychain，不得写入 UserDefaults、SQLite 明文字段、日志或导出的诊断包。

FR-008. 应用必须自动检测 uPic 的 bundle identifier 和可执行文件，不用用户手填路径。

FR-009. uPic 集成启用前必须上传一张应用生成的无隐私测试图，解析返回 URL 并通过 HTTPS `GET` 验证内容可访问。

FR-010. 测试上传失败时不得保存“配置成功”状态。

### 7.2 博主管理

FR-011. 支持单个输入、多行粘贴和 TXT/CSV 批量导入博主账号。

FR-012. 对输入统一去除 `@`、尾部 `/`、查询参数和大小写差异，再按 X 稳定 user ID 去重。

FR-013. 添加前通过官方 User Lookup 获取账号资料并预览，不根据输入字符串臆造账号身份。

FR-014. 账号改名后以稳定 user ID 关联历史记录，同时更新当前 handle；旧文件路径是否重命名由设置决定，默认不自动移动已有文件。

FR-015. 受保护、被暂停、不存在或当前凭证无权访问的账号必须单独标记，不得当作“0 篇文章”。

FR-016. 支持启用/暂停某个博主的后续同步；暂停不删除既有资料。

FR-016A. 侧边栏必须提供可见的“删除博主”操作及右键入口，并在执行前二次确认。v1 采用软删除：从跟踪列表隐藏并停止后续同步，但保留 Creator 主键、已下载文章、本地缓存和远程图床图片；用户再次添加同一 X user ID 时恢复原 Creator 身份并允许继续拉取。

FR-017. 支持导出博主清单为 CSV，包含显示名、handle、user ID 指纹、最近同步时间和完整性状态；不包含凭证。

### 7.3 文章发现

FR-018. 最近范围模式使用 `/2/users/:id/tweets` 分页获取。由于读取按返回的 Post 数计费，默认采用与目标 Article 数量匹配的小页（例如目标 10 篇时首批 20 条），并允许用户设置 50 / 100 / 300 / 1,000 / 3,200 条 Post 的扫描成本上限；不得无条件每页读取 100 条。

FR-019. 最近范围模式按页消费 `next_token`，直到找到用户选定的 X Article 数量、API 不再返回 token、达到官方上限、用户停止或出现不可恢复错误。返回文章按发布时间倒序截取最近 N 篇。

FR-020. 请求中获取识别与完整恢复所需字段，至少包括 `article`、`article_title`、`attachments`、`author_id`、`created_at`、`edit_history_*`，以及 `article.cover_media`、`article.media_entities` 和媒体扩展。

FR-021. 本地分类器必须以顶层官方 `article` 对象为唯一入选条件；不得以正文长度、`t.co` 链接、`note_tweet` 或线程总字数猜测 X Article。

FR-022. 完整历史模式使用 `/2/tweets/search/all`，查询以 `from:<handle>` 为主条件，并按时间区间与 `next_token` 分页。

FR-023. 完整历史任务开始前必须显示日期范围、预计最大读取量、访问要求和“该模式可能产生 X API 费用”的提示。

FR-024. 若完整历史接口返回权限不足，不得静默退化为最近范围；必须让用户明确选择是否降级。

FR-025. 文章分类器优先依赖结构化字段，不以页面文字或 URL 猜测 Article。

FR-026. `article.content_state` 存在时优先使用其结构化块；当前响应只提供 `article.plain_text` 时，必须完整保留全文和换行，不得回退到顶层 Post 的 `text` 或 `t.co` 入口链接。

FR-027. 每次发现任务保存扫描窗口、分页 token、最近/最老 Post ID、请求次数、结果数量和完整性状态。

FR-028. API 字段中出现未知结构时，解析器必须保留原始字段并跳过未知节点，不能让整个批次崩溃。

FR-028A. 支持一次粘贴 1–500 条 `x.com/<handle>/status/<post-id>` 或等价 `twitter.com` 链接；按 Post ID 去重并保留用户输入顺序，使用 `/2/tweets?ids=` 每批最多 100 条直接读取，不得为已知 Post ID 扫描作者时间线。

FR-028B. 直接链接返回后必须按原输入顺序恢复 Article，不受 API 响应数组顺序影响；普通 Post 单列为“不是官方 X Article”，删除、无权限或不可用 Post 单列为“不可用”，不能混入完成文章。

FR-028C. 链接下载默认查询本地稳定 Post ID。既有文章处于 committed 且 Markdown 文件仍存在时，默认零 API 请求跳过；用户可显式选择重新检查 X。直接 Lookup 不展开 author User 对象，使用 Post 自带 `author_id` 与链接 handle 关联，避免额外 User Read。

FR-028D. 已存在博主的刷新和全部增量同步必须复用本地稳定 X user ID，不得每次重复 User Lookup；只有首次添加或输入未命中本地 handle 时才查询用户资源。

### 7.4 内容获取与规范化

FR-029. 对每个 X Article 建立稳定主键：优先 Article ID，当当前 API 响应未返回 Article ID 时使用所属 Post ID；不得使用标题作为主键。

FR-030. 获取正文时保留标题、作者显示名、handle、源 URL、发布时间、更新时间、语言、原 Post ID、Article ID 和内容类型。

FR-031. 内部使用与 Markdown 无关的 `CanonicalDocument` AST 表示文章，节点至少支持：heading、paragraph、text span、list、quote、code、divider、table、image、link、embedded post 和 unsupported node。

FR-032. 所有正文转换都必须保持可见文字顺序；规范化换行和 Unicode 时记录算法版本。

FR-033. 标题缺失时，使用第一段第一句生成文件显示标题，最多 60 个可见字符；必须在 front matter 标记 `title_source: derived`，且不得调用 AI。

FR-034. URL 实体使用展开后的目标地址，显示文字尽量保留作者看到的文本；所有 URL 必须进行安全解析。

FR-035. 嵌入的 X Article/Post 卡片在原块位置转为唯一可点击的精确 `/status/` 或 `/article/` 链接；不复制卡片作者、摘要、日期和互动计数，也不得用作者主页代替文章链接。

FR-036. 不支持的节点在 Markdown 中插入明确注释，例如 `<!-- unsupported:x-article-node:type -->`，同时把原始结构保存在内部快照，不能静默丢弃。

FR-037. 正文获取和解析完成后计算源内容摘要，用于增量判断；摘要算法和规范化版本必须入库。

FR-038. 对同一文章的重复 API 结果做幂等合并，不生成多份文件。

### 7.5 图片下载、上传与替换

FR-039. 图片范围包括 `article.cover_media` 封面和 `article.media_entities` 声明的全部内文图片；不得把合并 `includes.media` 中属于其他 Post 的图片串入本文。

FR-040. 每张图片先下载到本地隐藏缓存，使用临时扩展名；下载完成后校验 MIME、文件头、长度和 SHA-256，再原子改名。

FR-041. 默认保留原始字节，不自动缩放、压缩、转码、去除色彩配置或删除 EXIF；若未来提供压缩，必须显式选择且默认关闭。

FR-042. 防止路径穿越、同名覆盖、超大文件和解压炸弹；单张图片默认上限 50 MB，超过时标为需用户确认。

FR-043. 图片缓存键使用源媒体稳定 ID + 内容 SHA-256；相同二进制只上传一次，但每篇文档仍保留各自图片节点和 alt text。

FR-044. 应用通过 bundle 检测 uPic，从 `~/Library/Containers/com.svend.uPic.macos/Data/Library/Preferences/` 只读取当前默认图床。v1 原生支持 uPic 中的 S3 / Cloudflare R2 默认项，不依赖 App Store 版不再提供的 CLI URL 标准输出。

FR-045. 默认 uPic 模式只在内存中使用当前 S3/R2 参数，不得回显、记录或发送密钥到本应用服务器。“从 uPic 导入 S3/R2”必须是用户显式触发的独立动作，且只有测试上传成功后才将密钥写入本应用 Keychain。

FR-046. 使用 uPic 当前默认 S3/R2 时，应用必须按本地文件路径映射每个远程 URL，验证 URL 数量与输入图片数量一致；任何数量不一致均视为失败。

FR-047. 上传返回必须是允许的 `https://` URL；默认拒绝 `file://`、`data:`、`javascript:`、环回地址和无法解析的结果。

FR-048. 每个远程 URL 至少执行一次带超时的可访问性验证；服务不支持 `HEAD` 时改用小范围 `GET`，并验证返回 MIME 为图片。

FR-049. 在所有图片验证通过前，Markdown 只写入同目录临时文件，不得替换最终文件。

FR-050. 部分上传失败时保存每张图的状态、尝试次数、最后错误和已获得 URL；重试仅处理未完成项。

FR-051. 若同一源图片内容未变化且已有成功远程 URL，增量同步不得重复上传。

FR-052. 若图床返回相同 URL 但远程内容校验不一致，标记冲突并停止提交该文章。

FR-053. 用户切换默认图床后，既有文章默认保持旧 URL；“迁移既有图片”作为独立、可预估、可恢复的 P1 任务，不能隐式执行。

### 7.6 Markdown 生成

FR-054. 默认每篇长文生成一份 UTF-8、LF 换行、扩展名为 `.md` 的文件。

FR-055. Markdown 顶部使用安全 YAML front matter，字段至少包括：

```yaml
---
title: "示例文章标题"
title_source: original
author_name: "示例作者"
author_handle: "@example"
content_type: x_article
source_url: "https://x.com/example/status/123"
source_post_id: "123"
source_article_id: "456"
published_at: "2026-09-04T08:00:00Z"
archived_at: "2026-09-04T09:00:00Z"
last_synced_at: "2026-09-04T09:00:00Z"
source_status: active
images_count: 3
content_checksum: "sha256:..."
exporter_version: "1.0"
---
```

FR-056. front matter 字符串必须正确转义，防止标题中的冒号、引号、换行或 `---` 破坏文档结构。

FR-057. 文件名默认格式为 `YYYY-MM-DD-标题--<postID末8位>.md`；非法文件名字符、控制字符和连续空格必须规范化。

FR-058. 同名冲突以稳定 ID 消解，不使用 `(1)`、`副本` 等不稳定后缀。

FR-059. 图片 Markdown 使用 `![alt text](https://...)`；alt text 优先使用源数据，缺失时使用“图片 01”等中性占位，不根据图片内容臆造描述。

FR-060. 图片出现顺序和对应段落位置必须与 CanonicalDocument 一致；封面默认放在 front matter 后、正文标题前。

FR-061. Markdown 必须包含一级标题；若源正文已用一级标题，则避免重复显示两次同名标题。

FR-062. 表格优先使用 GitHub Flavored Markdown；无法安全映射时使用原始 Markdown/安全 HTML 并加转换警告。

FR-063. 代码块保留语言提示（若有），代码内反引号长度冲突时自动选择更长围栏。

FR-064. 转换后必须运行内容一致性校验：规范化后的可见文字与源 AST 可见文字完全一致，图片节点数量完全一致，节点顺序可追溯。

FR-065. 一致性校验失败时不得覆盖既有 Markdown；保存诊断快照并把任务置为“转换失败”。

### 7.7 本地目录与索引

FR-066. 默认目录结构如下：

```text
用户选择的归档目录/
├── README.md
├── index.md
├── @author-a - Display Name/
│   ├── index.md
│   └── articles/
│       ├── 2026-08-01-标题一--12345678.md
│       └── 2026-08-15-标题二--87654321.md
├── @author-b - Display Name/
│   ├── index.md
│   └── articles/
└── .x-article-archiver/
    ├── archive.sqlite
    ├── source-snapshots/
    ├── assets-cache/
    ├── pending/
    ├── revisions/
    └── logs/
```

FR-067. 用户可读 Markdown 与内部状态分离；内部目录默认隐藏，但必须可通过设置中的“打开数据目录”访问。

FR-068. `index.md` 至少按博主列出标题、日期、类型、状态和相对链接，并在每次任务完成后原子更新。

FR-069. `archive.sqlite` 使用迁移版本，数据库升级失败时回滚并保留备份，不得破坏 Markdown 文件。

FR-070. 软件启动时检查临时文件、未提交事务和任务检查点；可安全恢复，不把 `.tmp` 文件当作正式文章。

FR-071. 用户在外部编辑 Markdown 后，默认不得被同步静默覆盖。写入前比较上次导出摘要；有本地修改时生成合并预览或新的 `.incoming.md`。

FR-072. 用户主动改名或移动 Markdown 后，软件可通过 front matter 中的稳定 ID 重新关联；重复 ID 必须提示冲突。

### 7.8 增量同步与版本

FR-073. 首次同步成功后记录每个博主的最新 Post ID、扫描窗口和同步时间。

FR-074. 后续同步优先使用 `since_id` 获取新增内容，并对近期可能编辑的内容做有限回查。

FR-075. 文章源摘要未变化时，跳过解析、图片上传和 Markdown 重写。

FR-076. 源内容变化时，在写入新版本前保存上一个由本应用生成的版本到 `revisions/`；修订文件包含时间和源摘要。

FR-077. 版本差异必须区分源内容变化与本地手工变化。

FR-078. 同步任务必须幂等：同一检查点重复执行，文章数、图片数和文件数不会增长。

FR-079. v1 支持手动“全部同步”和单博主同步；已存在的博主必须允许再次或多次拉取，并在每次开始前重新选择保存篇数或完整历史。手动“重新拉取”不得受上次 `since_id` 限制，但写入必须保持幂等：相同文章不重复、变化文章安全更新、新文章正常新增。每日/每周自动同步列为 P1。

FR-080. 自动重试采用指数退避并加入抖动；默认最多 5 次，429 必须尊重服务返回的重试时间。

### 7.9 任务控制与恢复

FR-081. 每篇文章使用状态机管理：`discovered → fetched → parsed → media_cached → media_uploaded → rendered → verified → committed`。

FR-082. 任何阶段失败都记录最后成功阶段，继续时从该阶段之后开始。

FR-083. 用户可以暂停任务；暂停应停止创建新网络请求，让正在进行的安全结束并提交检查点。

FR-084. 用户取消任务后，已提交文章保持不变，未完成文章进入“已取消，可继续”，不自动删缓存。

FR-085. 应用被强制退出或系统重启后，再启动必须识别中断任务并提供“继续”或“结束并保留缓存”。

FR-086. 写最终 Markdown、更新数据库与更新索引要使用可恢复的提交顺序，避免数据库显示成功但文件不存在。

FR-087. 应用必须限制并发：建议 API 请求 2、图片下载 6、图床上传 2；设置页可降低，不允许无限并发。

FR-088. 任务日志按任务保存，默认保留 30 天；诊断包生成前再次脱敏。

### 7.10 搜索、预览与导出

FR-089. 支持按标题、作者、正文全文和 front matter 搜索本地文章；搜索不依赖网络。

FR-090. 搜索索引可以使用 SQLite FTS5，索引损坏时可从 Markdown 重建。

FR-091. 预览器必须完整显示 X Article 的标题、全文结构、列表、引用、代码和全部图片，并显示图片加载失败状态；不得退化为只展示来源 Post 摘要或 Markdown 源文本，也不得执行文档中的脚本。

FR-092. 用户可一键打开 Markdown、在 Finder 中显示、复制本地路径或访问原文。

FR-093. v1 默认格式为 Markdown；可选同时导出原始结构 JSON 作为开发/诊断用途，但 UI 默认关闭。

FR-094. 重新导出必须使用已保存的 CanonicalDocument 和远程图片映射，不重新消耗 X API，除非用户选择“先刷新源内容”。

FR-094A. 文章行必须提供右键删除。执行前显示明确确认；确认后将该文章的 Markdown 和来源快照移入 macOS 废纸篓，删除数据库记录并重建相关索引。图片缓存和远程图床文件默认保留，界面必须明确说明这一边界。

FR-094B. “继续精确采集”队列必须可随时停止。停止后立即取消当前页面任务，不再自动进入下一篇；已提交文章保持不变，未完成任务在应用重启后仍可继续。

FR-094C. “继续精确采集”必须支持删除单个任务和清空全部任务，且执行前显示明确确认。删除“任务”不得误删已存在的 Markdown、全文快照、本地图片或图床图片；对已有归档只持久取消后续重试，对尚未产生归档的占位记录才删除数据库行。

FR-094D. 右上角“立即同步”必须先展示独立确认窗口，让用户选择每位已跟踪博主要检查的最近 1–100 篇，默认 10 篇。确认后后台同步，已完整归档文章自动跳过；过程与最终结果必须分别显示检查、保存、跳过、失败和图片数量，不与普通下载结果混用。

### 7.11 合规与内容状态

FR-095. 每篇 Markdown 必须保留作者、handle、发布时间和原文链接，不把归档内容伪装为用户原创。

FR-096. 应用必须在首次使用前展示本地归档、API 使用、版权和不得未经授权再发布的说明。

FR-097. 对通过 X API 存储的内容，后续同步必须检查编辑、删除、账号受保护、暂停和地区限制等状态。

FR-098. 检测到源内容删除或不可再用时，按合规策略更新或移除本地内容，并保留不含正文的墓碑记录（ID、原链接、检测时间、原因）。

FR-099. 正式版不得提供绕过平台删除、绕过受保护状态或关闭必要合规同步的开关。

FR-100. X API 访问终止或政策要求清除内容时，应用必须提供范围预览、可审计清单和符合当时适用条款的清理流程；具体期限上线前由法律/政策复核确认。

## 8. Markdown 映射规范

| 源结构 | Markdown 输出 | 校验要求 |
|---|---|---|
| Article title | `# 标题` | 文本一致；全篇仅一个主标题 |
| Heading 1–6 | `#`–`######` | 层级不越界；主标题冲突时下移正文标题层级 |
| Paragraph | 空行分隔段落 | 可见文字一致 |
| Bold | `**text**` | 样式区间不吞字符 |
| Italic | `*text*` | 与粗体嵌套合法 |
| Strikethrough | `~~text~~` | 无原生源样式时不添加 |
| Underline | `<u>text</u>` | 只允许固定安全标签 |
| Link | `[text](url)` | 文本、目标地址和顺序一致 |
| Ordered list | `1. item` | 项目数和嵌套层级一致 |
| Unordered list | `- item` | 项目数和嵌套层级一致 |
| Quote | `> text` | 多段引用连续、内容一致 |
| Code block | fenced code | 围栏不与代码内容冲突 |
| Inline code | `` `code` `` | 自动选取安全分隔符 |
| Divider | `---` | 前后保留空行 |
| Table | GFM table | 单元格顺序和内容一致；不支持时降级安全 HTML |
| LaTeX | `$...$` / `$$...$$` | 原始公式文本一致 |
| Cover image | 标题后第一张图 | 远程 URL 可访问 |
| Inline image | 原语义位置的 `![alt](url)` | 数量、顺序、alt 和 URL 映射一致 |
| Embedded X Article/Post | `引用文章：<https://x.com/.../status/...>` | 只保留精确内容链接，原块顺序不变，不夹带卡片元数据 |
| Unsupported node | HTML comment + 警告 | 原始节点保留在来源快照 |

### 8.1 文本一致性算法

1. 从源 AST 按阅读顺序提取可见文字序列。
2. 从生成 Markdown 解析回 AST，再提取可见文字序列。
3. 只规范化平台换行、Unicode NFC 和 Markdown 必需转义；不得忽略实际词句差异。
4. 两个序列必须 100% 一致；不一致则输出首个差异位置和上下文到脱敏诊断日志。
5. 图片稳定 ID 序列和嵌入 Post ID 序列必须分别 100% 一致。

### 8.2 最终文件提交规则

只有以下条件全部为真，文章才能进入 `committed`：

- 标题可用；
- 源身份字段完整；
- 正文可见文字一致；
- 图片节点数量一致；
- 每张图片有本地原始缓存；
- 每张图片有经过验证的 HTTPS 图床 URL；
- 临时 Markdown 可被解析；
- 最终目标路径无未处理冲突；
- 数据库事务和文件原子替换准备就绪。

## 9. 图床适配器设计

### 9.1 统一协议

```swift
protocol ImageHostAdapter {
    var displayName: String { get }
    func probe() async throws -> ImageHostCapability
    func upload(items: [CachedImage]) async throws -> [UploadResult]
    func verify(_ result: UploadResult) async throws -> RemoteImageMetadata
}
```

`UploadResult` 必须包含本地图片 ID、远程 URL、返回顺序、上传时间和适配器标识。不得只返回一段无法对应图片的 Markdown 字符串。

### 9.2 uPic 默认适配器

本机已检测到 uPic 1.4.9。v1 利用 uPic 已有的默认 S3/R2 图床配置：

```text
定位 uPic.app
  → 只读取沙盒偏好中的当前默认 host
  → 解析 S3/R2 endpoint、公开域名与 save key
  → 在内存中使用凭证执行 Signature V4 上传
  → 按本地路径映射远程 URL
  → 逐个进行远程验证
```

设计约束：

- 默认不复制、不持久化 uPic 密钥；
- 不直接编辑 uPic 配置；
- 不依赖剪贴板作为批量任务的数据通道；
- 不以“进程退出码为 0”单独判断上传成功；
- 不把进度文字误解析为 URL；
- uPic 配置结构变化或当前默认项不是 S3/R2 时，停止任务并给出可执行错误；
- 技术验证必须在当前已安装版本上用合成图验证上传、返回 URL 和 HTTPS 回读。

### 9.3 原生 S3/R2 适配器

作为 uPic 不可用时的后备：

- 支持 S3 Signature V4；
- 支持自定义 endpoint、bucket、region、public base URL 和 key prefix；
- Access Key / Secret Key 存 Keychain；
- 上传对象名使用 `x-archive/<author>/<yyyy>/<sha256>.<ext>`；
- 默认不覆盖同名对象；
- 测试时上传随机命名的小图，并验证公共 URL。

### 9.4 失败与回滚

图床通常不支持通用删除 API，因此“事务回滚”主要指本地提交回滚：

- 已成功上传但文章未提交的图片记录为 orphan candidate；
- 后续重试优先复用其 URL；
- 不自动删除远程对象，避免误删其他文章复用的图片；
- P1 提供孤立图片报告，由用户审核后再清理。

### 10.4 数据库幂等约束

- `Creator.x_user_id` 唯一；
- `ArticleRecord.stable_source_key` 唯一；
- `MediaRecord(article_id, source_position)` 唯一；
- `MediaBlob.sha256` 唯一；
- `UploadMapping(sha256, adapter_fingerprint)` 唯一；
- 每个任务状态转换带 compare-and-swap 版本号，避免重复并发提交。

### 10.5 原子提交顺序

```text
1. 写 source snapshot 临时文件
2. 写图片缓存临时文件并校验
3. 上传并验证所有远程图片
4. 生成 Markdown 临时文件并回读校验
5. 数据库开启事务，登记 pending commit
6. 将 Markdown 原子替换到最终位置
7. 更新数据库为 committed
8. 原子更新作者 index.md 和总 index.md
9. 清理临时文件
```

启动恢复时，若步骤 6 已完成但步骤 7 未完成，以 Markdown front matter 和摘要补齐数据库；若数据库显示 committed 但文件不存在，回退为 `render_pending` 并重新导出。

### 10.6 API 请求策略

- 同一 Post 尽量在列表请求中一次获取 Article、媒体和作者扩展，减少额外读取；
- 仅当列表字段不足时使用 Post Lookup 补取；
- 全局限流器按 endpoint 和凭证维度管理；
- 缓存 ETag/Last-Modified（若服务提供），但不能把 304 当作删除检测；
- 429 使用服务端 reset 时间；
- 401/403 不自动无限重试；
- 5xx、网络抖动和超时进入可恢复重试；
- 记录读取量估算和实际请求量，不记录 Bearer Token。

## 11. 首要技术验证门（开发前必须完成）

X 官方文档当前明确列出 Post 的 `article` 字段以及 `article.cover_media`、`article.media_entities` 扩展，但 Articles 专门章节主要描述创建草稿和发布。由于读取响应中的 Article 结构仍可能随访问等级或接口版本变化，不能只凭文档字段名就承诺 100% 还原。

正式开发前必须完成 P0 Spike：

### Spike A：Article 读取能力

使用用户有权读取的测试账号准备至少 3 篇文章：

1. 纯文本 + 多级标题 + 列表；
2. 封面 + 5 张内文图 + 链接；
3. 引用 + 代码块/表格/嵌入 Post。

分别通过 User Posts、Post Lookup 和 Full-Archive Search 验证：

- 能否发现 Article；
- `article` 是否包含完整标题和正文结构；
- 是否返回所有 inline media 的稳定关联；
- block/entity/range 的格式与 Unicode 索引单位；
- 编辑后字段变化；
- 删除后响应；
- 不同访问级别的差异。

通过标准：三篇不同排版的测试 X Article 中，可见文字、可获得的块顺序和图片数均可从官方响应完整恢复。

若不通过：不得偷偷改用浏览器抓取。应将发布范围调整为“官方 API 能完整返回的内容类型”，并提供两条经用户确认的替代方向：导入用户自己的 X 数据导出包，或等待/申请可满足读取需求的官方访问能力。

### Spike B：最近范围完整性

用同时包含回复、自线程、转帖、X Article 和 Note Post 的测试账号验证：

- 不使用 `exclude=replies` 时能扫描至官方范围上限；
- 本地过滤只让 X Article 入选，Note Post、线程和普通 Post 均不消耗用户选定的文章数量；
- 3,200 上限到达时界面明确标记；
- API 空结果与账号无文章、权限失败能被区分。

### Spike C：uPic 桥接

在当前安装的 uPic 上分别上传 1、2、10 张合成图片，验证：

- 应用未启动和已启动两种状态；
- 文件名含中文、空格、`#`、括号和 emoji；
- 输出 URL 数量、顺序和退出码；
- 单张失败时输出行为；
- 图床限流和断网恢复；
- 远程 URL 的 MIME 与内容哈希可验证程度。

若 uPic 当前版本不能稳定返回逐文件 URL，v1 必须切换为本应用原生 S3/R2 适配器，而不是依赖剪贴板猜测结果。

### Spike D：Markdown 保真

为所有 CanonicalDocument 节点建立金样本，执行“源 AST → Markdown → 解析 AST”的 round-trip 测试。可见文字、图片序列、链接目标、列表层级和代码必须全部通过。

## 12. 非功能需求

### 12.1 性能

NFR-001. 应用冷启动至主窗口可交互目标小于 2 秒（M3 Max，已有 10,000 篇索引时除外；索引加载必须异步）。

NFR-002. 除网络等待外，解析与 Markdown 生成吞吐不低于 100 篇/分钟（每篇 10,000 字符、10 张图片引用的基准夹具）。

NFR-003. 处理 1,000 篇、5,000 张图片的任务时，常驻内存目标低于 500 MB；不得一次把全部媒体载入内存。

NFR-004. 列表使用虚拟化渲染，10,000 篇记录滚动时主线程无持续卡顿。

NFR-005. 图片下载和上传采用流式文件 I/O，单张图片不做无必要的 Data 全量复制。

### 12.2 可靠性

NFR-006. 所有网络操作都有连接、首字节和总时长超时。

NFR-007. 任务检查点在每篇文章和每个分页完成后持久化。

NFR-008. 强制退出、断网、图床 5xx、X 429 和磁盘暂时不可写均有可复现的恢复测试。

NFR-009. 最终 Markdown 不允许零字节、不完整 YAML、临时图片地址或重复 front matter。

NFR-010. 数据库每日首次启动创建滚动备份，至少保留最近 3 个可用版本；Markdown 本身不依赖数据库才能阅读。

### 12.3 安全与隐私

NFR-011. 默认零遥测、零第三方崩溃上报；未来引入必须单独征得用户同意。

NFR-012. 正文仅发送到 X API 所需接口和用户选择的图床；图片不经过本应用开发者服务器。

NFR-013. 日志必须移除 Authorization、Cookie、签名查询参数、Access Key、Secret、完整本地用户名路径等敏感信息。

NFR-014. 预览器禁用任意 JavaScript、弹窗、下载、摄像头、麦克风、地理位置和跨域导航。

NFR-015. 所有从网络获得的标题、文件名、HTML、Markdown 和 URL 均视为不可信输入。

NFR-016. 诊断包生成前展示将包含的文件清单；不得自动上传，只保存到用户选择的位置。

NFR-017. 应用更新使用签名校验；不执行从归档内容或网络下载的脚本。

### 12.4 可访问性与本地化

NFR-018. v1 界面提供简体中文；架构保留英文 Localizable.strings。

NFR-019. 关键按钮、进度、错误和状态图标有 VoiceOver 标签，状态不只依赖颜色。每一个按钮、图标按钮和菜单入口在 macOS 上必须有简体中文鼠标悬停说明，说清所执行的动作；删除类操作还必须说明保留和删除的边界。

NFR-020. 支持键盘操作、系统深色模式、Reduce Motion 和文本缩放。

### 12.5 可维护性

NFR-021. X API 解码层保留未知字段，所有版本相关解析集中在适配器内。

NFR-022. Markdown 渲染算法、文件命名算法和 CanonicalDocument 都有显式版本。

NFR-023. 数据库迁移、缓存格式和 front matter 变更必须有向前迁移测试和回滚说明。

## 14. 错误分类与恢复矩阵

| 错误 | 是否自动重试 | 保留什么 | 用户动作 | 最终状态 |
|---|---:|---|---|---|
| X 429 限流 | 是，按 reset 时间 | 分页 token、已发现 ID | 可等待或暂停 | paused_rate_limit |
| X 5xx / 超时 | 是，最多 5 次 | 全部检查点 | 稍后继续 | retryable |
| X 401 | 否 | 已完成内容与检查点 | 重新连接 | needs_auth |
| X 403 权限不足 | 否 | 已完成内容与范围证据 | 降级模式或升级权限 | needs_access |
| API 用量不足 | 否 | 已完成内容与预计缺口 | 补充额度后继续 | needs_quota |
| 账号不存在 | 否 | 输入记录与错误 | 修正账号 | invalid_creator |
| 账号受保护 | 否 | 账号元数据 | 使用有权凭证或移除 | unavailable |
| 图片下载失败 | 是 | 文章结构、其他图片 | 重试 | media_pending |
| 图片校验失败 | 否 | 原始响应与临时文件 | 查看详情/跳过整篇 | media_invalid |
| uPic 未安装 | 否 | 所有本地原图 | 安装或换适配器 | needs_image_host |
| uPic 输出数量不符 | 否 | 本地原图、已解析 URL | 更新适配器后重试 | adapter_incompatible |
| 图床 4xx | 视错误而定 | 本地原图、已成功 URL | 修复配置 | upload_failed |
| 远程 URL 不可访问 | 是 | 本地原图、返回 URL | 重试验证/重传 | verify_failed |
| Markdown 一致性失败 | 否 | 源快照、AST、临时 Markdown | 导出诊断 | render_failed |
| 目录权限失效 | 否 | 数据库和缓存 | 重新选择同一目录 | needs_folder_access |
| 磁盘空间不足 | 否 | 已提交文件、检查点 | 释放空间 | needs_storage |
| 应用强退/系统重启 | 自动恢复 | 所有已提交阶段 | 继续或结束 | interrupted |

## 15. 验收标准

### AC-01：干净安装与启动

**前置**：一台未装开发环境的 M 系列 Mac。  
**步骤**：下载 DMG → 拖入 Applications → 首次启动 → 通过 Gatekeeper。  
**通过**：应用为 arm64，可正常显示原生界面；不要求安装 Rosetta、Homebrew、Python、Node 或浏览器插件；签名、公证和 stapling 验证通过。

### AC-02：首次配置与 uPic 默认图床

**前置**：本机已安装并配置 uPic。  
**步骤**：进入向导，选择目录，连接 X，自动发现 uPic，执行测试上传。  
**通过**：界面显示 uPic 与验证后的远程域名，不显示或复制 uPic 密钥；测试图返回 HTTPS URL且可访问；未验证时不能开始正式任务。

### AC-03：多博主批量归档

**前置**：3 个经授权的公开测试账号，各包含 X Article、Note Post、线程和普通短帖。  
**步骤**：多行粘贴 3 个账号，选择最近范围并开始。  
**通过**：账号身份正确；只导出 X Article；Note Post、线程、普通回复和转帖不误入；每个博主目录、文章文件和索引正确生成。

### AC-04：Article 排版保真

**前置**：金样本含标题、3 级标题、段落、粗斜体、下划线、链接、两级列表、引用、代码、表格、分隔线和嵌入 Post。  
**步骤**：归档并解析生成 Markdown。  
**通过**：可见文字 100% 一致；节点顺序一致；链接目标一致；代码无损；无法映射的节点明确标记；无 AI 改写。

### AC-05：图片全链路

**前置**：文章含封面和 12 张正文图片，其中两张二进制相同。  
**步骤**：执行归档。  
**通过**：13 个图片节点顺序正确；原图均有本地缓存；相同二进制只上传一次；Markdown 中 13 个引用均指向经过验证的远程 URL；图片未全部成功前文章不显示“完成”。

### AC-06：图床中断与续传

**前置**：上传 12 张图时在第 8 张断网。  
**步骤**：等待任务失败，恢复网络并点击继续。  
**通过**：前 7 张成功映射保留；从未完成项继续；不重复上传成功项；最终 Markdown 不含本地临时路径或空 URL。

### AC-07：应用强退恢复

**前置**：100 篇文章、500 张图片的运行中任务。  
**步骤**：在发现、下载、上传、写入阶段分别强制结束应用并重启。  
**通过**：每次都能识别中断任务；无损继续；无零字节文件、重复文件、重复图片上传或数据库假成功。

### AC-08：增量、编辑与本地手改冲突

**前置**：首次归档成功；随后源文章新增、编辑一篇，用户本地手改另一篇。  
**步骤**：再次同步。  
**通过**：只获取新增/需回查内容；新增文章创建；源编辑文章生成修订并更新；本地手改文章不被静默覆盖，生成可比较的 incoming 版本。

### AC-09：最近范围边界透明

**前置**：测试账号 Post 数超过 3,200。  
**步骤**：选择最近范围并完成分页。  
**通过**：软件显示实际扫描数、最早/最晚时间和 `RECENT_WINDOW_COMPLETE`；明确提示更早内容可能未覆盖；不得出现“全部历史已完成”。

### AC-10：完整历史

**前置**：具备 Full-Archive Search 权限和额度，测试账号有跨年内容。  
**步骤**：选择明确起止日期并完成所有分页。  
**通过**：显示预计与实际读取量；指定时间范围无分页缺口；状态为 `FULL_ARCHIVE_VERIFIED`；中途权限或额度失败则为 `PARTIAL`。

### AC-11：文件名和不可信输入

**前置**：标题含中文、emoji、斜杠、冒号、换行、`../`、引号和重复标题。  
**步骤**：批量导出。  
**通过**：文件均位于目标目录内；没有路径穿越；front matter 可解析；重复标题不覆盖；预览不执行脚本。

### AC-12：离线浏览

**前置**：已有归档结果。  
**步骤**：断网启动应用，搜索并打开文章。  
**通过**：本地索引、搜索、Markdown 文件和元数据可用；远程图加载失败有提示；同步按钮说明网络不可用，不破坏本地数据。

### AC-13：源内容删除或不可用

**前置**：已归档测试文章，随后从测试账号删除。  
**步骤**：运行合规同步。  
**通过**：应用识别状态变化，按最终批准的合规策略处理正文与图片引用，留下不含正文的墓碑记录；界面不再显示为 active。

### AC-14：密钥与日志安全

**步骤**：运行完整任务，导出诊断包，扫描应用设置、SQLite、日志、崩溃信息和输出文件。  
**通过**：不存在 X Bearer Token、uPic/S3 Secret、Authorization header、Cookie 或签名查询参数；Keychain 项访问控制正确。

### AC-15：精确采集停止、删除与防误操作

**前置**：建立包含未归档占位记录和已有 Markdown 重试记录的精确采集队列。  
**步骤**：在处理中点击停止；重启应用并继续；分别删除单个任务和全部任务；悬停检查主窗口、下载窗口、设置窗口及右键菜单的所有按钮。  
**通过**：停止后不再进入下一篇，队列可继续；删除任务需二次确认且已有归档不受影响；完成后被删任务不会在重启后再次出现；每个按钮的悬停文字能准确说明其作用。

### AC-16：独立批量同步

**前置**：至少跟踪两位博主，其中既有已完整归档文章，也有一篇新文章或未完成文章。  
**步骤**：点击右上角“立即同步”，分别验证取消和确认；选择每位最近 10 篇后开始，并观察发现与正文阶段。  
**通过**：点击时不会直接开始；确认窗口准确显示博主数、单人篇数与最大检查量；浏览器页面不展示；已完整归档文章跳过且不重复上传图片；状态持续显示检查、保存、跳过、失败和图片数；结束后独立同步结果与实际记录一致，X API 调用为 0。

### AC-17：定时同步与图床快捷入口

**前置**：跟踪至少两位博主，图床分别处于未连接和已验证状态。  
**步骤**：点击左下角图床未连接状态；配置每日时间和每位篇数并保存；验证 LaunchAgent plist 和注册状态；在应用关闭、应用已打开、系统睡眠错过时间和已有任务运行四种情况下验收。  
**通过**：图床状态直达配置第 2 节；定时设置持久化且 LaunchAgent 只有一份；到点后隐藏唤起并复用同一同步管线；睡眠错过后唤醒补执行；并发触发安全跳过；最近执行时间与结果可在弹窗查看；定时运行不弹出结果对话框，X API 调用为 0。

## 19. 风险与对策

| 风险 | 影响 | 概率 | 对策 |
|---|---|---:|---|
| X Article 读取字段不完整或变化 | 无法还原正文 | 高 | M0 实际 API Spike；防御性解析；不使用抓取兜底 |
| Full Archive 权限或费用不可用 | 不能承诺终身全部历史 | 高 | 两级模式；范围标记；任务前用量预估 |
| 时间线 3,200 上限 | 漏掉早期文章 | 高 | 明示边界；提供完整历史模式 |
| uPic 配置结构变化或默认项不是 S3/R2 | 无法使用当前默认图床 | 中 | 结构校验、可执行错误、手工原生 S3/R2 备选 |
| 图床上传部分成功 | 远程孤立图片、MD 不完整 | 高 | 两阶段提交、映射持久化、只重试失败项 |
| 用户外部修改 Markdown | 同步覆盖个人笔记 | 高 | 摘要检测、incoming 文件和差异预览 |
| 内容删除/版权请求 | 合规风险 | 中 | 官方 API、来源保留、状态同步、合规删除流程 |
| 大批量图片占满磁盘 | 任务失败 | 中 | 空间预估、流式下载、缓存上限和可恢复清理 |
| API 限流与按量计费 | 任务暂停或产生费用 | 高 | 请求合并、增量、预算提示、限流协调 |
| 恶意标题/Markdown/URL | 路径穿越或脚本执行 | 中 | 输入不可信模型、安全文件名、受限预览器 |
| App Sandbox 与 uPic 进程冲突 | 无法调用现有默认图床 | 高 | MVP 走 Developer ID 公证 DMG；Mac App Store 版改用原生适配器 |

## 20. 发布门槛（Definition of Done）

只有以下全部完成，才能称为“可交付 MVP”：

- Spike A–D 通过并保存脱敏证据；
- FR-001 至 FR-100 中标记为 v1 的需求已实现或经产品负责人书面降级；
- AC-01 至 AC-17 全部通过；
- 单元测试、集成测试、故障注入和真实联调无阻断缺陷；
- 从最终 DMG 安装的应用完成至少一次多博主、多文章、多图片的真实端到端归档；
- 最终 Markdown 的标题、可见文字、结构和图片得到自动校验，并进行人工抽检；
- 最近范围不会被错误标记为全部历史；
- 图片失败不会被错误标记为文章完成；
- 应用重启后任务可继续；
- 用户手工修改的 Markdown 不被静默覆盖；
- arm64、签名、公证、Gatekeeper、版本号和卸载测试通过；
- 日志、数据库、设置和安装包中无明文密钥；
- 隐私说明、X API 使用说明、版权边界和第三方许可证齐全。

## 21. 上线前待确认项

以下问题不阻止 M0 技术验证，但在进入正式开发前需要产品负责人确认：

1. 内容范围已确认为仅 X Article；Note Post、普通 Post 和同作者线程不导出。
2. 完整历史模式产生的 X API 用量由谁承担；本 PRD默认使用用户自己的 Developer 凭证和额度。
3. 源文章删除后本地 Markdown 的最终处理策略，需以届时 X 条款与用户法律意见为准。
4. 是否默认永久保留本地原图缓存；本 PRD 当前默认保留，以保证图床失败可恢复。
5. 本地手工编辑冲突时，是偏向保留本地、保留源版本，还是提供逐段合并；本 PRD 当前选择“绝不静默覆盖，生成 incoming 版本”。
6. 是否需要在 MVP 就支持定时同步；本 PRD 当前放在 P1，MVP 只做手动同步。

## 22. 参考依据（截至 2026-09-04）

- [X User Posts 时间线集成说明](https://docs.x.com/x-api/posts/timelines/integrate)：官方说明 User Posts 时间线最多返回最近 3,200 条，单页最多 100 条；请求端排除 replies 时最多 800 条。
- [X User Posts API 参数](https://docs.x.com/x-api/users/get-posts)：当前字段列表包含 `article`，扩展包含 `article.cover_media` 与 `article.media_entities`。
- [X Articles API 简介](https://docs.x.com/x-api/articles/introduction)：Article 支持富文本、媒体和嵌入 Post；当前专门章节描述创建草稿和发布能力，因此读取结构必须用真实 API 做前置验证。
- [X Full-Archive Search Quickstart](https://docs.x.com/x-api/posts/search/quickstart/full-archive-search)：完整历史可追溯到 2006 年，需要 Self-serve/按量或 Enterprise 访问，支持分页和作者查询。
- [X API 价格](https://docs.x.com/x-api/getting-started/pricing)：截至 2026-09-04，Post Read 为每个返回资源 US$0.005；资源在同一 UTC 日内通常去重计费。产品必须提供扫描成本闸门、本地缓存和直链 Lookup。
- [X Post Lookup](https://docs.x.com/x-api/posts/lookup/introduction)：`GET /2/tweets` 单次最多可按 ID 读取 100 个 Post，适合已知 Article 链接的低成本批量直取。
- [X Developer Policy](https://docs.x.com/developer-terms/policy)：涉及官方 API、离线存储、内容更新/删除、授权和隐私要求。
- [X Post 展示要求](https://docs.x.com/developer-terms/display-requirements)：要求保留来源、作者身份、时间和原文完整性；X 不替第三方作者提供版权许可。
- [Apple：访问 macOS App Sandbox 外文件](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox)：用户选择目录和持久目录访问应使用系统文件选择与 security-scoped bookmark 思路。
- [uPic 官方开源仓库](https://github.com/gee1k/uPic)：uPic 是 macOS 原生图床客户端，支持命令行上传并可输出 URL/Markdown 等格式。
